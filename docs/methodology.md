# Methodology

## 1. Overview

This project implements a comparative credit-scoring framework using the Home Credit Default Risk dataset. The objective is to estimate Probability of Default (PD) under a common experimental environment, compare multiple modelling approaches, combine selected models through stacking, calibrate the resulting probability, and connect the final PD to an illustrative financial risk framework.

The implemented workflow is:

Data → Cleaning and Feature Engineering → Train/Validation/Test Split → Model-Specific Preprocessing → Base Models → Out-of-Fold Stacking → Probability Calibration → Financial Analysis and Explainability → Flask API → React Dashboard → Docker

## 2. Dataset

The implementation uses `application_train.csv` from the Home Credit Default Risk dataset.

- Observations: 307,511
- Original columns: 122
- Target: `TARGET`
- Default proportion: approximately 8.07%
- Non-default proportion: approximately 91.93%

The class imbalance makes accuracy unsuitable as the sole evaluation metric. Model evaluation therefore considers ROC-AUC, PR-AUC, F1 Score, and Brier Score.

## 3. Data Cleaning and Feature Engineering

The Home Credit `DAYS_EMPLOYED` variable contains the sentinel value `365243`. This value was treated as an anomalous value rather than a genuine employment duration.

The implementation retained an anomaly indicator and engineered more interpretable variables:

- `AGE_YEARS`
- `EMPLOYED_YEARS`
- `DAYS_EMPLOYED_ANOM`

The final predictor set excludes:

- `SK_ID_CURR`
- `TARGET`
- `DAYS_BIRTH`
- `DAYS_EMPLOYED`

The resulting modelling dataset contains 121 predictors: 105 numerical and 16 categorical variables.

## 4. Data Partitioning

The data was separated approximately as follows:

| Partition | Observations | Approximate Share |
|---|---:|---:|
| Training | 215,257 | 70% |
| Validation | 46,127 | 15% |
| Test | 46,127 | 15% |

Splitting was performed before operations that could learn from or synthesize observations.

Preprocessing was fitted using training data and subsequently applied to validation/test data. Where SMOTE was evaluated, synthetic observations were restricted to training procedures.

## 5. Base Models

Three main modelling families were evaluated.

### Logistic Regression

Logistic Regression provides the conventional linear/statistical baseline.

A separate Weight of Evidence (WoE) Logistic Regression implementation was retained as a traditional scorecard-style and interpretability benchmark.

The regular preprocessed Logistic Regression, rather than the WoE model, is used as the Logistic Regression component of the final stacking ensemble.

### XGBoost

XGBoost provides a nonlinear tree-based benchmark capable of modelling feature interactions and nonlinear relationships.

### Multi-Layer Perceptron

A PyTorch Multi-Layer Perceptron provides the neural-network benchmark.

Its preprocessing, model metadata, and trained state are saved separately for deployment.

## 6. Class Imbalance Experiments

The project evaluated both class weighting and SMOTE rather than assuming that either technique would automatically improve the final system.

Class weighting increased the importance of minority-class defaults during training but substantially changed probability behaviour.

SMOTE generated synthetic minority-class observations within training procedures but did not provide sufficient overall improvement for the probability-focused objective.

The final stacking system therefore uses the untreated baseline versions of:

- Logistic Regression
- XGBoost
- MLP

## 7. Stacking Ensemble

The final ensemble uses out-of-fold (OOF) predictions from the three base models.

For each training observation, its OOF probability is generated by a model that was not trained on that observation. This reduces leakage when training the second-level model.

The meta-features are:

- Logistic Regression PD
- XGBoost PD
- MLP PD

A Logistic Regression meta-learner combines these probabilities to produce the raw ensemble PD.

## 8. Probability Calibration

Because the final PD is used directly in financial calculations, probability quality is important in addition to discrimination.

The project compares:

- Raw stacking probability
- Platt scaling
- Isotonic regression

Isotonic regression is used for the deployed final PD because it produced the lowest recorded Brier Score among the compared final calibration outputs.

A methodological limitation is that the calibration alternatives were compared on the held-out final evaluation set. A stronger experimental design would select the calibration method using a separate calibration/validation procedure before one final untouched test evaluation.

## 9. Financial Framework

The calibrated PD is translated into an illustrative Expected Loss calculation:

`Expected Loss = PD × LGD × EAD`

where:

- PD = calibrated Probability of Default
- LGD = Loss Given Default scenario assumption
- EAD = Exposure at Default

The prototype uses `AMT_CREDIT` as a proxy for EAD rather than estimating a separate EAD model.

The dashboard supports multiple LGD scenarios. Changing LGD changes the financial consequences but does not change the model-generated PD.

The indicative-rate prototype uses:

`Indicative Rate = 0.09 + (PD × LGD)`

The fixed 9% component is a simplified research assumption representing non-PD pricing components. It is not a real-world bank pricing policy.

## 10. Explainability

SHAP is used to provide feature-level explanations for the XGBoost component.

The deployed service transforms the applicant through the XGBoost preprocessing pipeline and uses a tree-based SHAP explainer to identify important local drivers.

These SHAP values explain the XGBoost component only. They are not an exact decomposition of the final stacked and calibrated PD and should not be interpreted as causal effects.

## 11. Deployment Methodology

The final modelling pipeline is served through:

- Flask REST API
- React frontend
- Docker containers
- Docker Compose

Saved preprocessing objects and model artifacts are used so that new applicant records are transformed consistently with the training workflow.

The implemented deployment is a local containerized research prototype. Public cloud deployment is outside the current implemented scope.
